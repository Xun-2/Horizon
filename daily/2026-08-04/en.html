Background

Large language models normally require enough memory to hold their weights during inference, so models with tens of billions of parameters commonly exceed the RAM available on consumer devices; for comparison, conventional local configurations list roughly 18 GB for Qwen 3.6-27B and 22 GB for Qwen 3.6-35B-A3B. Swiftlet instead targets ordinary Apple devices with a memory-efficient approach, claiming that its 35B model can run natively on an iPhone 17 using about 2.5 GB of RAM.

Impact

Mac and iPhone developers may be able to test much larger Qwen models locally, although the lack of performance and storage-impact data makes production suitability uncertain.

Community Discussion

Commenters welcomed the experiment as progress toward more capable on-device AI and suggested that larger RAM caches on 24-32 GB Macs could improve speed. Others questioned the project's implied novelty by citing similar weight-streaming demonstrations, including a claimed 400-billion-parameter model on an iPhone, while concerns remained about performance and storage wear.

ComfyUI Adds Day-Zero Support for MiniMax H3

ComfyUI has added day-zero support for the open-weight MiniMax H3 video model, bringing native audio and video generation at resolutions up to 2K into local node-based workflows. The reported optimization replaces pruned modulation weights—about 40% of the model’s parameters—with a functionally equivalent lookup table, while claiming no reduction in output quality.

Details and sources

ComfyUI has added day-zero support for the open-weight MiniMax H3 video model, bringing native audio and video generation at resolutions up to 2K into local node-based workflows. The reported optimization replaces pruned modulation weights—about 40% of the model’s parameters—with a functionally equivalent lookup table, while claiming no reduction in output quality. Alongside dynamic VRAM offloading, the smallest variant is said to reduce memory use by 66%, from 123.6 GB at full precision to 42.5 GB, potentially allowing the 2K model to run locally on hardware such as an RTX 3060. However, the available material provides no complete benchmarks, compression methodology, or safety evaluation with which to verify the quality and memory claims.

Background

Large language model serving is constrained by GPU memory, especially when the system stores a key-value (KV) cache of prior attention states for each active request. Quantizing the KV cache and compressing model weights can reduce memory use and improve serving efficiency, while integrity checks are intended to help verify that deployed model components have not been altered.

Practical consequence

Inference users should verify both model quality and data-handling policies rather than assuming that unquantized model weights imply an unquantized KV cache or zero-data-retention service.

Hijacking LiteLLM to Intercept and Forge AI Traffic

LiteLLM centralizes access to multiple model providers, keeping real provider credentials server-side while clients use virtual gateway keys. The author argues that this convenience makes the gateway a high-value target: possession of a proxy-admin credential can expose conversations and proprietary context, enable inference billed to the victim, and permit response tampering without changing client configurations.

Details and sources

Background

LiteLLM centralizes access to multiple model providers, keeping real provider credentials server-side while clients use virtual gateway keys. The author argues that this convenience makes the gateway a high-value target: possession of a proxy-admin credential can expose conversations and proprietary context, enable inference billed to the victim, and permit response tampering without changing client configurations.

Solution

In a lab demonstration, the author uses documented management functionality to change two routing settings—api_base and use_litellm_proxy—so the victim gateway forwards requests through an attacker-controlled LiteLLM instance while users retain their existing endpoint and credentials. Because the victim must attach its decrypted backend provider key to upstream requests, the malicious gateway can capture that key at TLS termination; custom authentication hooks first harvest it, after which the attacker provisions matching provider routes and transparently relays traffic. Supported post-call and streaming hooks then expose or modify conversations, inject fabricated text, and forge tool calls after model inference, placing the manipulation beyond prompt-level defenses, although client-side tool approval still applies unless automatic execution is enabled. The author’s llm-heist workflow demonstrates harvesting, provisioning, hijacking, monitoring, injection, and route recovery, while noting that reroutes remain visible in model metadata and may briefly disrupt clients in the manual harvesting mode. Recommended defenses include monitoring route and callback changes, forwarding audit logs to a SIEM, restricting gateway egress and provider keys by IP, rotating credentials, reconciling provider billing, limiting administrative exposure, and promptly patching LiteLLM and its host.

Takeaway

The central claim is that an AI gateway is not merely an observability layer but a security boundary: one compromised administrative credential can grant centralized control over credentials, data, model outputs, and potentially agent actions.
