Hijacking LiteLLM to Intercept AI Gateway Traffic

LiteLLM centralizes access to multiple LLM providers, keeps provider credentials server-side, and exposes a unified API with virtual keys, making it useful for governance but also a high-value target. Background

LiteLLM centralizes access to multiple LLM providers, keeps provider credentials server-side, and exposes a unified API with virtual keys, making it useful for governance but also a high-value target. The author argues that compromising a proxy-admin credential, such as the master key, could let an adversary affect an organization's traffic without changing client configurations; the demonstrated scenario is a lab technique intended for authorized red-team or purple-team operations.

Solution

The attack changes two documented model settings through LiteLLM's management API: api_base points to an attacker-controlled gateway and use_litellm_proxy enables proxying, while users continue contacting the familiar endpoint with the same virtual key. Because the victim gateway resolves backend provider credentials before forwarding requests, the rerouted request exposes those credentials to the attacker's server, where a custom authentication hook can harvest them; the attacker then provisions matching endpoints and forwards traffic normally. Hooks such as async_post_call_success_hook and async_post_call_streaming_iterator_hook allow response interception and modification after model inference, including forged text or tool calls that prompt-level defenses never saw. The author's walkthrough uses separate harvest, provision, hijack, monitoring, injection, and recovery stages, and notes that tool execution still depends on client-side authorization unless an agent runs in an automatic mode. Suggested defenses include monitoring routing and callback changes, auditing gateway activity through a SIEM, restricting egress and provider keys by source IP, rotating credentials, limiting administrative exposure, patching LiteLLM, and reconciling provider billing; the evidence remains a practical demonstration rather than a measure of prevalence.

Takeaway

The author's central conclusion is that an AI gateway is a control point for confidentiality, spending, response integrity, and agent behavior, so a single administrative compromise can have organization-wide consequences. Securing the gateway therefore requires treating configuration changes, credentials, outbound access, and downstream response integrity as security-critical surfaces.
