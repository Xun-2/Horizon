Kumo Tabular：表格预测的准确率与效率前沿

企业中的客户、交易、传感器和订单数据大多以表格存在，但传统梯度提升树的工作流仍需为每个新任务收集标签、设计特征、搜索超参数并单独训练模型。 文章认为，类似大语言模型上下文学习的方式可以改变这一流程：模型预先学习大量表格结构，推理时只需提供带标签的示例行，就能直接预测新行。

详情与原文

企业中的客户、交易、传感器和订单数据大多以表格存在，但传统梯度提升树的工作流仍需为每个新任务收集标签、设计特征、搜索超参数并单独训练模型。文章认为，类似大语言模型上下文学习的方式可以改变这一流程：模型预先学习大量表格结构，推理时只需提供带标签的示例行，就能直接预测新行。

背景

企业中的客户、交易、传感器和订单数据大多以表格存在，但传统梯度提升树的工作流仍需为每个新任务收集标签、设计特征、搜索超参数并单独训练模型。文章认为，类似大语言模型上下文学习的方式可以改变这一流程：模型预先学习大量表格结构，推理时只需提供带标签的示例行，就能直接预测新行。

方案

NVIDIA Kumo Tabular 是一个面向分类和回归的开放基础模型，拥有2800万至2.15亿参数，能够在一次前向计算中输出类别概率或数值预测，无需训练、调参或手工特征工程。其 Transformer 先用细胞嵌入处理数值、类别和缺失值，再交替使用列注意力理解某个值在列分布中的意义、行注意力建模特征交互，最后让查询行关注带标签的上下文行；上下文键值可复用，Test-GQA 则缩小了查询缓存，回归还会输出999个分位数以估计不确定性。为避免表格变长后注意力变得过于分散，模型按键数量对注意力温度进行对数缩放。预训练完全依赖结构因果模型生成的合成表格，生成器随机组合因果图、函数、缺失模式、异常值、重复行冲突、高基数类别和重尾目标，并分三个阶段把上下文规模扩展到6万行；小型、中型和大型模型分别见过约3500万、7100万和1.37亿张人工表格。发布方报告称，三个模型在 TabArena、BeyondArena、TALENT 和 ScoringBench 上均取得领先或前列成绩，Kumo Tabular 在统一 RTX 6000 Pro 环境下的运行速度据称比 LimiX-2 快17倍，但训练配方和数据生成器尚未公开，主要结果也仍是发布方自测。

启示

文章的核心结论是，面向表格结构的预训练、分层注意力和合成数据，可能同时推进表格模型的准确率、推理效率与免训练使用方式。不过，模型目前只直接支持数值和类别列，面对远超训练范围的数据或上下文与查询分布不一致的情况，性能可能下降，部署前仍需用独立留出数据验证准确率与校准性。

让事实与来源都经得起验证

在多工具 MCP Agent 中，事实正确并不代表来源归因正确。 文章将这种错误称为“跨来源混淆”：例如退款期限确实存在于政策文件，却被回答成来自客户账户记录；在医疗场景中，患者病史中的信息若被说成医学文献结论，也会造成数据敏感的误导。

详情与原文

在多工具 MCP Agent 中，事实正确并不代表来源归因正确。文章将这种错误称为“跨来源混淆”：例如退款期限确实存在于政策文件，却被回答成来自客户账户记录；在医疗场景中，患者病史中的信息若被说成医学文献结论，也会造成数据敏感的误导。传统事实性验证把所有工具输出合并为匿名证据池，因此可能判定这类回答得到支持，却无法检查回答所声称或暗示的来源是否真的支持该事实。

背景

在多工具 MCP Agent 中，事实正确并不代表来源归因正确。文章将这种错误称为“跨来源混淆”：例如退款期限确实存在于政策文件，却被回答成来自客户账户记录；在医疗场景中，患者病史中的信息若被说成医学文献结论，也会造成数据敏感的误导。传统事实性验证把所有工具输出合并为匿名证据池，因此可能判定这类回答得到支持，却无法检查回答所声称或暗示的来源是否真的支持该事实。

方案

ProvenanceGuard 是叠加在黑盒 MCP Agent 之后的验证层，不需要重新训练原 Agent，而是读取保留工具输出和来源 ID 的 MCP trace，并逐条拆分回答、为每个声明寻找相关来源、检查来源是否支持声明，再核对回答明示或暗示的来源，最后给出逐条判定及整篇回答的放行或拦截决定。实验配置使用 MiniLM 做来源路由、DeBERTa NLI 模型做支持判断、本地语言模型做声明拆分，并特别检查数字、日期和标识符是否确实出现在来源中；经过校准后，被拦截的回答还可进入 RARR 风格的修复流程并重新验证。基于 281 条医疗 Agent trace 和留出的 40 个回答、361 条人工评估声明，专家认为 139 条不应通过，系统捕获了其中 138 条，但也拦截了 67 条本应支持的声明；可识别来源的准确选择率约为 86%。在同一测试集上，其拒绝 F1 为 0.802，高于 MiniCheck 的 0.783、RAGAS Faithfulness 的 0.758、AlignScore 的 0.662 和 SummaC-ZS 的 0.436，并且能够输出逐条的声明到来源映射；对人为替换来源的 50 个样例则全部识别出来。代价是对相似来源的区分仍较弱，相关测试中的精确来源识别率只有 50.3%；修复虽解决了 173 个被拦截回答，但其中 144 个最终只是回退文本，离线运行的报告配置约为每个回答增加半秒延迟。作者还强调，这些模型和指标是论文的本地实验配置，迁移到托管模型或其他领域仍需重新测试和校准。

启示

文章的核心结论是，在多来源 Agent 中，“事实是否存在”与“事实究竟来自哪里”应当作为两个可审计的问题分别验证。ProvenanceGuard 证明了保留来源身份能够提高对错误归因的识别能力，但其误拦截、相似来源判别和修复质量也表明，来源感知验证仍是谨慎的审查层，而不是已经解决的事实性保障方案。
